# uplab.tilda — API для разработчиков

Помимо автоматической замены тегов `[UPLABTILDA ...]`, модуль предоставляет
публичный PHP-API для программного доступа к данным Tilda Publishing.

## Подключение модуля

```php
\Bitrix\Main\Loader::includeModule('uplab.tilda');
```

После этого доступны все классы в пространстве имён `Uplab\Tilda`.

---

## Получение данных из Tilda API

Все методы используют кэш (7 дней). При первом вызове данные запрашиваются из
Tilda API; при повторных — возвращаются из кэша.

### Список проектов

#### Обработанные данные (заголовки очищены от кавычек, приведены к кодировке сайта)

```php
use Uplab\Tilda\Common;

$projects = Common::getProjects();
// [
//   ['id' => '123', 'title' => 'Мой проект', 'descr' => '...', ...],
//   ...
// ]
```

#### Сырые данные (как возвращает Tilda API, без обработки)

```php
$projects = Common::getRawProjectsData();
// Те же поля, но title/descr не очищаются от кавычек и не конвертируются
```

---

### Список страниц проекта

#### Обработанные данные

```php
$pages = Common::getPages(123456); // projectId
// [
//   ['id' => '789', 'title' => 'Главная', 'descr' => '...', 'alias' => '/', ...],
//   ...
// ]
```

#### Сырые данные

```php
$pages = Common::getRawPagesData(123456);
```

#### Ассоциативный массив id → title (для `<select>`)

```php
$options = Common::getAssocPagesList(123456);
// ['789' => 'Главная', '790' => 'О компании', ...]
```

---

### Данные конкретной страницы

#### Сырые данные страницы (полный ответ API без обработки HTML)

```php
$page = Common::getRawPageData(789); // pageId

// Доступные ключи:
// $page['id']         — id страницы
// $page['title']      — заголовок
// $page['descr']      — описание
// $page['alias']      — псевдоним (slug)
// $page['date']       — дата публикации
// $page['html']       — полный HTML документа (<!DOCTYPE html>...)
// $page['js']         — массив подключённых JS-файлов
// $page['css']        — массив подключённых CSS-файлов
// $page['images']     — массив изображений
// $page['projectid']  — id проекта

echo $page['title'];
echo strlen($page['html']); // размер HTML
```

Этот метод удобен, если нужно самостоятельно разобрать HTML, извлечь ресурсы
или применить собственную трансформацию перед встраиванием в страницу.

---

### Обработанный HTML для встраивания в шаблон Битрикс

Эти методы используются внутри при замене тегов, но доступны и напрямую.

```php
// Режим по умолчанию: ассеты + body, обёрнуто в маркеры <!--<TILDA>-->
$html = Common::getPageContent(789);

// Полный HTML страницы (режим HIDEPAGETEMPLATE=Y)
$fullHtml = Common::getPageFullContent(789);

// Разделённые ассеты и body (режим MOVERESOURCESTO=HEADEND/BODYEND)
$parts = Common::getPageParts(789);
// $parts['assets'] — стили и скрипты
// $parts['html']   — тело страницы
```

## Проверка подключения к Tilda API

```php
use Uplab\Tilda\Request;

$data = Request::checkConnection($publicKey, $secretKey);

if ($data === false) {
    // ошибка транспорта или невалидный ответ (детали в логе)
} elseif ($data['status'] === 'FOUND') {
    $count = count($data['result'] ?? []);
} else {
    $apiMessage = $data['message'] ?? '';
}
```

## Прямые запросы к Tilda API (с кэшем)

Низкоуровневый доступ через `Request::getData()`. Используется методами `Common`
внутри; полезен если нужен метод, которого ещё нет в `Common`.

```php
use Uplab\Tilda\Request;
use Uplab\Tilda\Common;
use Uplab\Tilda\Enum\ApiMethod;

Common::getOptions(); // загружает ключи API

$result = Request::getData(ApiMethod::PAGE_FULL, ['pageid' => 789]);
```

Допустимые методы — константы `ApiMethod`:

| Константа                  | Строка             |
|----------------------------|--------------------|
| `ApiMethod::PROJECTS_LIST` | `getprojectslist`  |
| `ApiMethod::PAGES_LIST`    | `getpageslist`     |
| `ApiMethod::PAGE_FULL`     | `getpagefull`      |

Базовый адрес API берётся из настройки `UPT_API_URL` — его можно менять на месте,
если Tilda сменит адрес или запросы нужно пустить через свой прокси. Домен не
ограничен; проверяются только протокол HTTPS и наличие хоста в адресе.
Некорректное значение заменяется на
`Common::DEFAULT_API_URL`, на странице настроек модуля выводится сообщение
об ошибке с фактически используемым адресом, а в лог пишется запись уровня
`warning`; использование нестандартного адреса отмечается на уровне `debug`.

## Событие перед вставкой контента

Подпишитесь на событие `onBeforeContentReplace`, чтобы модифицировать HTML
страницы Tilda непосредственно перед встраиванием в страницу.

```php
// В своём модуле (например, в include.php)
\Bitrix\Main\EventManager::getInstance()->addEventHandler(
    'uplab.tilda',
    'onBeforeContentReplace',
    function (&$content) {
        // $content — HTML страницы Tilda (передаётся по ссылке)
        $content = str_replace('старый текст', 'новый текст', $content);
    }
);
```

## Очистка кэша

```php
use Uplab\Tilda\Service\Cache;

Cache::clearAllCache();         // полная очистка (все страницы + списки)
Cache::clearListCache();        // только списки проектов/страниц
Cache::clearPageCache($tag);    // конкретная страница ($tag = md5 URL запроса)
```

## Логирование

Включается в настройках модуля: **Настройки → Настройки модулей → Интеграция с Tilda.cc → Логирование**.

| Уровень   | Что пишется                                                                                                           |
|-----------|-------------------------------------------------------------------------------------------------------------------------|
| `debug`   | найденные на странице теги и режим вставки, вызовы методов, HTTP-запрос и ответ (код, размер, время, начало тела), cache hit/miss, размеры разобранного HTML |
| `info`    | сохранение ответа в кэш с кратким описанием результата (число проектов/страниц либо id, заголовок и размер HTML страницы) |
| `warning` | ответ без результата (`status` ≠ `FOUND` или пустой `result`), срабатывание fallback-парсинга `#allrecords`, отклонённый адрес API |
| `error`   | ошибки cURL / `file_get_contents`, ошибки Tilda API, нечитаемый JSON                                                    |

Строка журнала: `2026-06-15 17:50:38 DEBUG [uplab.tilda] HTTP request {"url":"…"}` —
дата, уровень, сообщение и контекст в JSON.

Ответ Tilda пишется **целиком, без обрезки**, отдельным блоком после строки —
так его можно скопировать и разобрать как обычный HTML:

```
2026-06-15 17:50:39 DEBUG [uplab.tilda] HTTP response received {"http_code":200,"bytes":189432,"duration_ms":412}
--- body ---
<!DOCTYPE html>
…
--- end body ---
```

Из-за полных ответов файл журнала растёт быстро, поэтому предел размера поднят
до 32 МБ (`Logger::MAX_FILE_SIZE`) — по достижении ядро копирует журнал
в `*.log.old` и начинает новый. Штатного лимита `FileLogger` в 1 МБ хватало бы
на пару страниц.

Имя файла: `tilda_{salt}_{date}.log`. `salt` — 32-символьная hex-строка, генерируется
один раз при первой записи и сохраняется в опции `UPT_LOG_SALT`. Делает URL файла
непредсказуемым при прямом переборе, если каталог всё же отдаётся веб-сервером.

**Каталог логов** задаётся одной опцией `UPT_LOG_DIR`; как трактовать значение,
видно по нему самому:

| `UPT_LOG_DIR`        | Итоговый путь                                                                                                     |
|----------------------|--------------------------------------------------------------------------------------------------------------------|
| пусто (по умолчанию) | `logs/` внутри установленного модуля — `/bitrix/modules/uplab.tilda/logs/` либо `/local/modules/uplab.tilda/logs/` |
| `upload/tilda_logs`  | `{DOCUMENT_ROOT}/upload/tilda_logs/` — путь без ведущего слэша считается от корня сайта                            |
| `/var/log/tilda`     | `/var/log/tilda/` — путь со слэшем (или с буквой диска) считается абсолютным                                       |

Путь для каталога модуля определяется через `getLocalPath()`, поэтому установка
в `/local/modules/` (в том числе через composer) обрабатывается корректно.
Значение игнорируется, если содержит `..` либо каталог непригоден для записи
(не существует и не может быть создан) — тогда используется каталог модуля.
Фактический путь всегда виден на странице настроек модуля.

Каталог создаётся автоматически с правами `0750`.

**Защита от HTTP-доступа:**

| Сервер           | Что делать                                                                                          |
|------------------|-----------------------------------------------------------------------------------------------------|
| Apache/LiteSpeed | Ничего — `.htaccess` создаётся при первой записи автоматически                                       |
| nginx            | Ничего, если каталог оставлен по умолчанию: `/bitrix/modules/` и `/local/` закрыты штатным конфигом Битрикса. Для своего каталога внутри сайта добавьте правило: |

```nginx
location ^~ /upload/tilda_logs/ {
    deny all;
}
```

Рядом создаётся `.access.php` (`$PERM["/"]["*"] = "D"`) — запрет каталога
средствами самого Битрикса. Он действует на запросы, которые обрабатывает ядро,
и дополняет `.htaccess`, а не заменяет его: статические файлы веб-сервер отдаёт
мимо ядра.

`.htaccess` не только запрещает доступ (директивы и для Apache 2.4, и для 2.2),
но и обезвреживает скрипты — тем же способом, каким Битрикс защищает `/upload/`:
для `.php`, `.phtml`, `.cgi`, `.pl`, `.py` и подобных расширений обработчик
подменяется на `text/plain` (`SetHandler`/`ForceType`) и выключается движок PHP
(`php_flag engine off` внутри `<IfModule mod_php*.c>`). Так посторонний файл,
попавший в каталог, нельзя будет выполнить через веб. Файл перезаписывается, если
его содержимое разошлось с эталоном, — обновление модуля обновляет и защиту.

Каталог вне `DOCUMENT_ROOT` (абсолютный путь) недоступен по HTTP по определению —
`.htaccess` в него не пишется.

Дополнительно страница настроек показывает файлы каталога, которых модуль не
создавал (всё, кроме `tilda_{salt}_{дата}.log`, `*.log.old`, `.htaccess` и
`.access.php`) — чтобы чужой файл не лежал там незамеченным. Программно этот
список доступен через `Logger::findForeignFiles()`.

Кнопка «Очистить логи» удаляет только файлы модуля; посторонние она не трогает,
а перечисляет в ответе — чтобы случайно не снести то, что положили не мы.

Из кода можно обращаться к логгеру напрямую:

```php
use Uplab\Tilda\Diag\Logger;

Logger::debug('Моё сообщение', ['pageId' => 789, 'source' => 'my-module']);
Logger::info('Страница получена', ['bytes' => strlen($html)]);
Logger::warning('Нестандартная ситуация', ['reason' => '...']);
Logger::error('Критическая ошибка', ['exception' => $e->getMessage()]);

// Маскировка ключей API в URL перед логированием:
// secretkey скрывается целиком, publickey — частично (abcd***wxyz)
$safeUrl = Logger::maskUrl($url);
```

Логгер по умолчанию **выключен** (`UPT_LOG_ENABLED = N`). Пишет только если
уровень сообщения ≥ настроенному минимуму (`UPT_LOG_LEVEL`).

## Структура классов

```
Uplab\Tilda\
├── Common          — фасад API: getProjects, getPages, getRawPageData и др.
├── Request         — HTTP-клиент к Tilda API (с кэшем через Service\Cache)
├── Helper          — утилиты: кодировки, события, уведомления об ошибках
├── Replace         — замена тегов [UPLABTILDA ...] в буфере вывода
├── Events          — обработчики событий ядра Битрикс
├── Diag\
│   └── Logger      — файловый логгер поверх Bitrix\Main\Diag\FileLogger
├── Model\
│   └── CacheTable  — ORM-сущность таблицы tilda_pages_cache
├── Service\
│   └── Cache       — сервис кэширования поверх Bitrix\Main\Data\Cache
└── Enum\
    ├── ApiMethod           — допустимые методы Tilda API (PROJECTS_LIST / PAGES_LIST / PAGE_FULL)
    └── MoveResourcesTarget — режимы выноса ассетов (NONE / HEADEND / BODYEND)
```

> **Обратная совместимость.** Имена `Uplab\Tilda\Cache`, `Uplab\Tilda\CacheTable`
> и `Uplab\Tilda\Logger` работают как `class_alias`-псевдонимы (файлы
> `lib/cache.php`, `lib/cachetable.php`, `lib/logger.php`), но помечены
> как `@deprecated` — используйте новые пространства имён.
