# История изменений

Все значимые изменения модуля «Интеграция с Tilda» (`uplab.tilda`).

Формат основан на [Keep a Changelog](https://keepachangelog.com/ru/1.1.0/),
версионирование — [Semantic Versioning](https://semver.org/lang/ru/).

---

## [3.3.3] — 2026-08-20

Tilda периодически обрывает отдачу тяжёлых страниц: приходит около 90% ответа,
дальше сервер молчит, не закрывая соединение, — запрос висел до конца таймаута
и падал с `curl errno 28`, а блок Tilda исчезал со страницы сайта. По журналу
событий видно, что сбои идут пачками в один день (истёк кэш → неудача →
следующий хит пробует снова) и заканчиваются успехом со второй-третьей попытки.
Версия делает из этого выводы.

### Добавлено

- **Повтор запроса при обрыве передачи.** Число попыток задаёт опция
  `UPT_REQUEST_ATTEMPTS` (по умолчанию 3, максимум 5). Повтор выполняется только
  для кодов cURL, означающих обрыв или неудачу соединения, а не отказ по существу
  (`Request::RETRYABLE_CURL_ERRORS`: 6, 7, 18, 28, 35, 42, 52, 55, 56); между
  попытками — пауза 250 мс. Все попытки делят общий бюджет
  `UPT_CURLOPT_TIMEOUT`: три попытки не превращают прежний 15-секундный предел
  в 45 секунд. Уведомление администратору и запись об ошибке уходят один раз,
  когда исчерпаны все попытки, — иначе один сбой давал бы три сообщения об одном
  и том же. В журнале каждая повторяемая попытка фиксируется как `warning`,
  окончательная неудача — как `error`.
- **Детектор зависшей передачи** — опция `UPT_STALL_TIMEOUT` (по умолчанию
  5 секунд, 0 — не проверять). Реализован через `CURLOPT_PROGRESSFUNCTION`:
  если байты уже шли и новых нет дольше заданного времени, запрос прерывается
  с кодом 42 и попытка считается неудачной. Ожидание первого байта детектор
  не трогает — холодная генерация страницы в Tilda занимает секунды и обрывать
  её нельзя. Без детектора зависшая передача занимала весь `UPT_CURLOPT_TIMEOUT`,
  и на повтор в пределах разумного времени ответа страницы места не оставалось.
- **Отдача устаревшей копии страницы при сбое Tilda** — опция
  `UPT_STALE_ON_ERROR`, **по умолчанию выключена**. Пока она выключена,
  поведение прежнее: блок Tilda при сбое исчезает со страницы. Когда включена —
  при подтверждённой транспортной ошибке отдаётся последняя успешно загруженная
  версия страницы. Ответ API `ERROR`, не-`FOUND` или пустой результат копией не
  подменяется: страница могла быть удалена либо снята с публикации. Об отдаче
  копии сообщается сразу в четырёх местах, чтобы старая версия на проде не
  превратилась в новый баг:
  - красная плашка в админке с названием страницы и датой копии (через
    `Helper::notifyOnce()` — одна на состояние, а не на каждый хит); снимается
    автоматически, как только страница загрузилась заново;
  - запись уровня `warning` в журнале модуля и запись в журнале событий Битрикса;
  - столбец «Состояние кэша» в списке закэшированных страниц
    (`admin/cache_table.php`): актуален / истёк / истёк, при сбое отдаётся копия /
    истёк, копии больше нет;
  - пометка на самой странице: HTML-комментарий `<!-- uplab.tilda: stale cache … -->`
    выводится всегда, видимая полоса — только пользователям с правом на модуль
    (`>= R`). Посетитель сайта не видит ничего. Работает во всех трёх режимах
    вставки, включая `HIDEPAGETEMPLATE=Y` (там пометка вставляется после `<body>`).
  - Резервная копия хранится отдельно от основного кэша, в каталоге
    `cache_tilda_stale`, со сроком 30 дней (`Cache::STALE_TTL`) — она нужна ровно
    тогда, когда основной кэш уже истёк. Копия ведётся только для контента
    страниц; для списков проектов и страниц она не нужна. Перезаписывается при
    каждой успешной загрузке. При обновлении с предыдущей версии отсутствующая
    копия создаётся из ещё живого основного кэша без продления исходного
    30-дневного срока. Наличие копии отмечается отдельной маленькой записью:
    проверка состояния не читает повторно полный HTML тяжёлой страницы.
    Удаляется при очистке кэша страницы, полной очистке кэша и при удалении кэша
    в мастере деинсталляции: явный сброс означает «забыть эту страницу».
    Принудительное обновление ссылкой `?clear_cache=Y` файлов не удаляет, поэтому
    там копия остаётся доступной.

### Изменено

- `Request::makeRequest()` разделён на `attemptCurl()` и `attemptStream()` —
  одна попытка каждой транспортной ветки, — плюс цикл попыток и единая
  `reportFailure()`. Поведение веток не изменилось: те же опции cURL, та же
  политика HTTPS-only и проверки сертификата, тот же контекст потока для
  `file_get_contents()`.
- В сообщении об ошибке появилось число выполненных попыток, а при срабатывании
  детектора — текст «передача оборвалась: за N с не пришло ни одного нового
  байта» вместо `Operation timed out`: причина по журналу теперь читается
  однозначно.
- `Cache::clearAllCache()` и `Cache::clearPageCache()` чистят и каталог
  резервных копий; `clearPageCache()` дополнительно снимает плашку об
  устаревшей копии.
- Столбец состояния проверяет фактическое наличие резервной копии, а не делает
  вывод только по дате последней загрузки.

### Известные ограничения

- Отдача копии рассчитана на обычные хиты публичной части. При принудительном
  обновлении ссылкой `?clear_cache=Y` ядро форсирует промах кэша, и прочитать
  копию в этом хите может не получиться — тогда поведение будет прежним, как
  с выключенной опцией.

## [3.3.2] — 2026-08-17

### Исправлено

- **Журнал больше не растёт без предела.** Файл журнала назывался
  `tilda_{salt}_{дата}.log`: каждый день создавался новый, и ни один старый не
  удалялся — при надолго включённом уровне `debug` каталог логов пух неограниченно.
  Теперь запись идёт в один файл `tilda_{salt}.log`, а ядро при достижении
  `Logger::MAX_FILE_SIZE` копирует его в `tilda_{salt}.log.old` и обнуляет текущий.
  В каталоге всегда не больше двух файлов, занятое место ограничено сверху
  удвоенным лимитом (64 МБ) и не зависит от времени работы.
- Список «посторонних файлов» на странице настроек (`Logger::findForeignFiles()`)
  распознаёт и новое имя, и файлы прежней схемы — накопленные журналы не
  помечаются как чужие.

### Добавлено

- **Сведения о журналах прежнего формата на странице настроек**: сколько файлов
  осталось от посуточной схемы и сколько места они занимают
  (`Logger::findLegacyLogs()`). Сам модуль их не удаляет — журнал может
  понадобиться для разбора инцидента, а удаление на обычном хите публичной части
  прошло бы незаметно для администратора. Удаляет их кнопка «Очистить логи»,
  которая и раньше захватывала оба формата имени.
- **Сообщение о сбое загрузки из Tilda больше не выглядит успешным.** Уведомление
  в админке создавалось с типом `CAdminNotify::TYPE_NORMAL`, а ядро рисует таким
  типом зелёный блок с галкой — ошибка читалась как «всё в порядке». Теперь
  используется `TYPE_ERROR` (красная плашка). То же для разовых уведомлений
  `Helper::notifyOnce()`, у которых появился необязательный параметр типа.

## [3.3.1] — 2026-08-17

Страница, созданная в Tilda, не появлялась в списке редактора, попап открывался
тем дольше, чем больше проектов в аккаунте, а сбой Tilda приводил к пустой
странице на сайте.

### Исправлено

- **Пустая страница при сбое Tilda.** В режиме `HIDEPAGETEMPLATE=Y` пустой ответ
  API заменял весь буфер вывода, и посетитель получал документ нулевой длины
  с кодом 200. Теперь остаётся страница шаблона сайта, а служебный тег
  `[UPLABTILDA ...]` вырезается из вывода (`lib/replace.php`).
- **Ответ без содержимого больше не кэшируется на неделю.** Ответ Tilda со
  статусом, отличным от `FOUND`, либо с пустым `result` для контента страницы
  прерывает кэширование (`abortDataCache()`) и сообщается администратору. Раньше
  такой ответ сохранялся на семь дней, и статья пропадала с сайта до ручной
  очистки кэша. Для списков пустой `FOUND` по-прежнему валиден: проект без
  страниц — нормальный ответ.
- **Чекбокс «Не выводить шаблон сайта» в попапе редактора** не имел атрибута
  `value`, поэтому отправлялось `on`, а сервер ожидал `Y` — режим
  `HIDEPAGETEMPLATE=Y` из попапа не включался.
- **Гонка при записи кэша.** Если параллельный процесс успевал записать кэш
  между проверкой и попыткой записи, метод возвращал пустой результат при живых
  данных. Теперь кэш перечитывается.
- **Тег с `PAGE=0`** больше нельзя вставить в редактор: при пустом списке страниц
  сохранение отклоняется с сообщением «Выберите страницу».

### Добавлено

- **Отдельный срок кэша списков** — опция `UPT_LIST_CACHE_TTL`, по умолчанию
  600 секунд (`Cache::DEFAULT_LIST_TTL`). Контент страниц кэшируется как прежде,
  на 7 дней (`Cache::DEFAULT_TTL`). С общим недельным сроком новая страница Tilda
  не появлялась в редакторе до ручной очистки кэша списков.
- **Ленивая загрузка страниц в попапе редактора.** Раньше при открытии
  запрашивался список страниц для каждого проекта аккаунта последовательно —
  при холодном кэше время открытия равнялось числу проектов, умноженному на
  таймаут запроса. Теперь загружается только выбранный проект, остальные — по
  смене значения в списке через AJAX-действие `getPages` в `tools/post.php`.
  - список уже загруженных проектов кэшируется в памяти окна, повторный выбор
    запроса не делает; кэш живёт только пока открыт попап;
  - перебор проектов с клавиатуры не шлёт запрос на каждый шаг (пауза 250 мс);
  - у запроса есть предел ожидания (30 секунд) и обработка сбоев: индикатор
    загрузки не может зависнуть навсегда;
  - ответ устаревшего запроса не перезаписывает список актуального проекта.
- **Различение «в проекте нет страниц» и «список не загрузился».** Оба случая
  давали пустой выпадающий список, и сбой Tilda читался как отсутствие страниц.
  Теперь при ошибке выводится сообщение и кнопка «Повторить».
  Новые методы: `Common::getAssocPagesResult()`, `Service\Cache::getLastError()`.
- **Диагностика обрыва запроса.** В журнал и уведомление администратора при
  ошибке cURL добавлены описание запроса (метод и id страницы/проекта, без
  ключей — `Request::describeRequest()`), HTTP-код, длительность запроса и число
  полученных до обрыва байт. Одинаковый размер от попытки к попытке означает, что
  поток встаёт на одном месте, а не что сеть работает нестабильно.
- **Невалидный ответ API** теперь попадает и в журнал событий Битрикса, а не
  только в файловый журнал, который по умолчанию выключен.

### Изменено

- **Права в `tools/post.php` проверяются по действию:** чтение списка страниц
  (`getPages`) требует права `R`, изменяющие действия — очистка кэша, очистка
  логов, проверка подключения — по-прежнему `W`.
- **Сообщения журнала уровней `error` и `warning` переведены в языковые файлы**
  (`lang/ru`, `lang/en`): `lib/replace.php`, `lib/request.php`, `lib/common.php`,
  `lib/service/cache.php`. Отладочная трассировка уровня `debug` (имена вызванных
  методов, cache hit/miss) осталась техническими маркерами на английском.

### Безопасность

- Данные, встраиваемые в тело `<script>` попапа (заголовки страниц Tilda),
  кодируются с `JSON_HEX_TAG`: заголовок вида `</script>…` не может закрыть тег.
- `Helper::notifyError()` экранирует внешний текст (сообщение Tilda API, ошибка
  cURL) через `htmlspecialcharsbx` перед выводом в `CAdminNotify`: шаблон
  уведомления содержит разметку и рендерится в админке как HTML. В журнал
  событий уходит исходный текст — там экранирует ядро.
- Языковые строки, попадающие в JS-контекст, экранируются `CUtil::JSEscape`
  в `admin/menu.php` и `install/bitrix/components/uplab/tilda/.parameters.php`
  (в списке страниц это было сделано в 3.3.0).

## [3.3.0] — 2026-06-15

### Добавлено

- **Файловый логгер** `Uplab\Tilda\Diag\Logger` поверх `Bitrix\Main\Diag\FileLogger`
  (`lib/diag/logger.php`). Уровни `debug` / `info` / `warning` / `error`, суточные
  файлы. Журнал ведётся по всей цепочке — от найденного на странице тега до
  вставленного HTML: режим вставки и id страницы, запрос к API, ответ (код,
  размер, время, начало тела), статус Tilda и краткое описание результата,
  попадания и промахи кэша, размеры разобранного HTML, срабатывание
  fallback-парсинга `#allrecords`, ошибки транспорта и API.
  - Ответ Tilda пишется целиком, без обрезки, отдельным блоком
    `--- body --- … --- end body ---`, чтобы HTML можно было разбирать прямо
    из журнала. Предел размера файла поднят с 1 МБ (штатный для `FileLogger`)
    до 32 МБ, дальше ядро ротирует журнал в `*.log.old`.
  - Логирование по умолчанию выключено (`UPT_LOG_ENABLED = N`), файлы и каталог
    создаются только после включения.
  - Каталог логов задаётся одной опцией `UPT_LOG_DIR`: пусто — `logs/` внутри
    установленного модуля (по умолчанию; путь корректно определяется и для
    `/local/modules/`, такой каталог закрыт от HTTP штатными правилами Битрикса),
    путь без ведущего слэша — от корня сайта, со слэшем — абсолютный путь
    на хостинге. Непригодный для записи каталог игнорируется, логи идут
    в каталог модуля; фактический путь показан на странице настроек.
  - Имя файла: `tilda_{salt}_{date}.log`, где `salt` — 32 hex-символа,
    генерируется один раз (`random_bytes`) и хранится в опции `UPT_LOG_SALT`;
    делает имя файла непредсказуемым при переборе.
  - Каталог создаётся с правами `0750`; если он внутри `DOCUMENT_ROOT`, в него
    кладётся `.htaccess`: запрет доступа (Apache 2.4 и 2.2) плюс обезвреживание
    скриптов тем же способом, каким Битрикс защищает `/upload/` — `SetHandler`/
    `ForceType text/plain` для `.php`, `.phtml`, `.cgi`, `.pl`, `.py` и подобных
    и `php_flag engine off`. Рядом создаётся `.access.php`
    (`$PERM["/"]["*"] = "D"`) — запрет каталога средствами ядра Битрикса.
    Оба файла обновляются, если разошлись с эталоном. Правило для nginx
    приведено в `DEVELOPER.md`.
  - Страница настроек показывает файлы каталога, которых модуль не создавал
    (`Logger::findForeignFiles()`), — посторонний файл не останется незамеченным.
    Кнопка «Очистить логи» удаляет только файлы модуля, а посторонние
    перечисляет в ответе, не трогая их.
  - Ключи API в URL маскируются (`Logger::maskUrl()`) до любой записи: секретный —
    целиком, публичный — частично.
  - `Logger::clearLogs()` — удаление всех файлов журнала.
- **Вкладка «Логирование» в настройках модуля** (`options.php`): опции
  `UPT_LOG_ENABLED` (по умолчанию `N`), `UPT_LOG_LEVEL` (по умолчанию `error`),
  `UPT_LOG_DIR`, показ фактического каталога с индикатором его наличия,
  кнопка «Очистить логи».
- **Кнопка «Проверить подключение»** в настройках: `Request::checkConnection()`
  выполняет некэшируемый запрос `getprojectslist` с введёнными ключами и
  сообщает результат — количество найденных проектов либо текст ошибки API/cURL.
  AJAX-обработчики `uTildaCheckConnection()` и `uTildaClearLogs()` в `script.js`.
- **Разовые уведомления** `Helper::notifyOnce()` / `Helper::clearNotifyOnce()`:
  состояние запоминается в опции, поэтому сообщение показывается один раз и
  не возвращается после закрытия, а журнал событий не растёт на каждом хите.
  Используется для некорректного адреса Tilda API.
- **Мастер удаления модуля** (`install/unstep1.php`): выбор, что удалять вместе
  с модулем — файлы кэша, таблица `tilda_pages_cache`, файлы логов, настройки
  модуля. Шаг подтверждения защищён `check_bitrix_sessid()`.
- **`Uplab\Tilda\Enum\ApiMethod`** (`lib/enum/apimethod.php`) — единый источник
  истины для имён методов API (`getprojectslist`, `getpageslist`, `getpagefull`)
  и их валидации; заменил разбросанные строковые литералы и локальный allowlist
  в `Request`.
- **Публичный API для разработчиков**: `Common::getRawProjectsData()`,
  `Common::getRawPagesData()`, `Common::getRawPageData()` — сырые данные Tilda API
  без обработки HTML и конвертации кодировки.
- **`DEVELOPER.md`** — описание публичного PHP-API модуля, событий, логирования
  и структуры классов.

### Изменено

- **Реорганизация пространств имён**: `Uplab\Tilda\Cache` → `Uplab\Tilda\Service\Cache`
  (`lib/service/cache.php`), `Uplab\Tilda\CacheTable` → `Uplab\Tilda\Model\CacheTable`
  (`lib/model/cachetable.php`). Прежние имена сохранены как `@deprecated`
  `class_alias`-псевдонимы (`lib/cache.php`, `lib/cachetable.php`), поэтому код
  на стороне сайта, обращавшийся к ним, продолжает работать. Псевдоним
  `Uplab\Tilda\Logger` → `Uplab\Tilda\Diag\Logger` добавлен там же.
- **Из запросов к Tilda убраны cookie и авто-Referer.** Раньше cURL получал
  `CURLOPT_COOKIEFILE`/`CURLOPT_COOKIEJAR` с общим файлом
  `/upload/tilda_cookie.txt` и `CURLOPT_AUTOREFERER`; `CURLOPT_MAXREDIRS`
  снижен с 10 до 3. Файл cookie больше не создаётся и не читается — оставшийся
  от прежних версий можно удалить вручную. Запись в CHANGELOG добавлена
  постфактум, в 3.3.0 это изменение не было отражено.
- `Request` разделён на методы `resolveApiUrl()`, `buildUrl()`, `makeRequest()`,
  `checkConnection()`, `getData()`; сборка URL вынесена из `getData()`.
- Таблица `tilda_pages_cache` при удалении модуля сносится только по явному
  выбору в мастере удаления, а не всегда.
- Минимальная версия ядра поднята до `main` >= 21.900.0 (требуется `FileLogger`).
  То же значение проставляется в `version_control.txt` пакета обновления, чтобы
  обновление не устанавливалось на несовместимое ядро.
- В `composer.json` добавлено требование `ext-json`.
- В `admin/editor_popup.php` при неудачной загрузке модуля выводится сообщение
  `ACCESS_DENIED` вместо `uplab.tilda_NO_MODULE`.
- **Переформулированы сообщения модуля.** Первая строка одинакова и коротка —
  название модуля («Интеграция с Tilda», `uplab.tilda`), что не сработало и
  ссылка на журнал событий; ответ сервиса вынесен на вторую строку и взят
  в кавычки, поэтому длинный текст ошибки не растягивает первую фразу.
  Сообщения не утверждают, что «остальной сайт работает»: страница может
  целиком приходить из Tilda (`HIDEPAGETEMPLATE=Y`). Уведомление о сбое загрузки
  перестало быть «красной» ошибкой (`CAdminNotify::TYPE_NORMAL`), в журнале
  событий записи идут с уровнем `WARNING` вместо `ERROR`.

### Исправлено

- Ответ Tilda API со статусом `ERROR` больше не создаёт запись в реестре
  `tilda_pages_cache`: раньше в списке «Страницы» появлялись строки без названия,
  за которыми не стояло закэшированного контента (`lib/service/cache.php`).
- `Common::getPageParts()` вызывал событие `onBeforeContentReplace` даже когда
  ответ API был пустым — обработчики получали пустую строку.
- `options.php`: обращение к `$_REQUEST['save']` без проверки существования
  (на PHP 8 — warning и deprecated-вызов `strlen(null)`).
- `Cache::cache()`: чтение `arrResponse` из кэша без проверки ключа.

### Безопасность

- **Только HTTPS для запросов к Tilda API.** Значение опции `UPT_API_URL`
  принимается, лишь если это HTTPS-адрес с указанным хостом; иначе используется
  адрес по умолчанию, на странице настроек показывается сообщение об ошибке
  с фактически используемым адресом, а факт отклонения пишется в лог
  (`Request::resolveApiUrl()`). Домен не ограничивается — адрес API остаётся
  настраиваемым на месте. `Request::makeRequest()` дополнительно отклоняет любой
  не-HTTPS URL. Для cURL добавлены `CURLOPT_PROTOCOLS`/`CURLOPT_REDIR_PROTOCOLS`
  = `CURLPROTO_HTTPS`, явные `CURLOPT_SSL_VERIFYPEER`/`CURLOPT_SSL_VERIFYHOST`
  и `CURLOPT_MAXREDIRS = 3`. Закрывает утечку ключей по открытому каналу и SSRF
  через понижение протокола при редиректе.
- Шаг удаления модуля требует валидный `sessid`.
- Запасной транспорт `file_get_contents()` (используется, когда в PHP нет cURL)
  приведён к той же политике, что и cURL-ветка: редиректы не выполняются
  (`follow_location = 0`), поэтому ответ `302 Location: http://…` больше не может
  увести запрос с ключами API на открытый канал; заданы проверка сертификата
  (`verify_peer`, `verify_peer_name`), таймаут из настроек модуля и общий
  User-Agent. Ответ со статусом 3xx фиксируется в журнале, код ответа пишется
  в лог, а тело ошибок 4xx/5xx больше не теряется (`ignore_errors`) — сообщение
  Tilda доходит до администратора.
- Страница настроек `options.php` явно проверяет права: без успешного
  `Loader::includeModule()` и права на модуль `>= R` страница ничего не выводит,
  сохранение опций требует `>= W`, а при праве только на чтение кнопка
  «Сохранить» не показывается. Раньше ядро пускало к странице при праве `R`,
  а сохранение внутри файла ограничивалось только `check_bitrix_sessid()`.
- В `admin/cache_table.php` языковая строка в JS-контексте подтверждения
  удаления экранируется через `CUtil::JSEscape`.

- `README.md` и полный текст лицензии GPL-3.0 в `LICENSE.txt`; GPL-заголовки
  добавлены во все PHP-файлы модуля.

### Изменено

- `tools/post.php` отвечает JSON (`Bitrix\Main\Engine\Response\Json`) вместо
  голого текста; клиентские функции показывают результат через уведомление.

### Безопасность

  регуляркой `^[a-f0-9]{32}$` — произвольная строка не попадёт в `cleanDir()`/`delete()`.
- Удаление выполняется в транзакции с проверкой права `>= W` и `check_bitrix_sessid()`.
